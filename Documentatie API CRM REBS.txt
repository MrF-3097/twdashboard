Documentație API
Parcurgerea feed-ului
Pentru importul proprietăților din CRM REBS, se va consuma un feed JSON care conține o listă
cu detaliile tuturor proprietăților active.
Recomandăm parcurgerea feed-ului la un interval prestabilit de timp (de exemplu o oră) printr-un
mecanism de gen Cron. Job-ul cron va parcurge toate proprietățile din feed, va salva proprietățile
noi în baza de date proprie, va actualiza proprietățile care au fost modificate, și le va șterge pe
cele care nu mai apar în feed.
Feed-ul este disponibil la /api/public/property/
Există și un feed pentru toti agenții activi, disponibil la /api/public/agent/
Autentificare
Pentru autentificarea la API, se folosește o cheie API care trebuie transmisă la accesarea
oricărei resurse API.
Cheia API poate fi specificată printr-un parametru GET cu numele api_key sau prin header-ul
HTTP Authorization.
De exemplu, dacă cheia API este abcdef, se poate accesa API-ul în următoarele moduri:
● Prin parametru GET: /api/public/property/?api_key=abcdef
● Prin header-ul HTTP Authorization (exemplu folosind curl):
○ curl -H "Authorization: abcdef" http://towerimob.crmrebs.com/api/public/property/
Dacă echipa REBS nu v-a transmis o cheie API, vă rugăm să ne contactați la
suport@crmrebs.com și să includeți în CC și pe managerul companiei pentru care se
implementează API-ul.
Câmpul "meta"
Pentru evitarea timpului de răspuns mare și a unei dimensiuni mari, recomandăm parcurgerea
API-ului folosind paginare. Pentru aceasta, se va folosi câmpul meta din răspuns.
Câmpul meta conține informații utile pentru paginare:
● limit - numărul maxim de proprietăți returnate într-o pagină
● next - URL-ul către pagina următoare, dacă există
● offset - numărul proprietății de la care se returnează proprietăți pentru această pagină
● previous - URL-ul către pagină anterioară, dacă există
● total_count - numărul total de proprietăți (pentru toate paginile)
Pentru o parcurgere cât mai ușoară a API-ului, se poate face un request inițial pentru prima
pagină, iar apoi se parcurge pagină cu pagină folosind câmpul next, până când acesta devine
null.
În mod implicit, o pagină conține 20 de proprietăți. Se pot cere mai multe proprietăți folosind
parametrul limit.
Exemplu:
● Se accesează prima pagină: /api/public/property/
● Se accesează apoi câmpul meta.next din răspuns:
/api/public/property/?offset=20&limit=20
● Și așa mai departe, până când câmpul meta.next devine null, moment în care au fost
parcurse toate proprietățile

Imagini
Imaginile redimensionate la maxim 1920 px x 1080 px sunt returnate în câmpul resized_images,
reprezentat printr-o listă de URL-uri către imagini.
Imaginile neredimensionate sunt returnate în câmpul full_images.
Aceste imagini nu pot fi folosite direct în site. Ele trebuie descărcate, stocate pe serverele
site-ului și servite de acolo către vizitatori.
Pentru a seta un watermark pe toate imaginile, trimite-ne la adresa suport@crmrebs.com o
imagine semitransparentă (PNG).
Ordonare
Ordonare
Proprietățile returnate pot fi ordonate specificând parametrul order_by, ce va avea ca valoare
numele câmpului după care se va face ordonarea. În mod implicit, ordonarea se face crescător.
Pentru ordonare descrescătoare, se va adaugă “-” (caracterul minus) în fața câmpului după care
se face ordonarea.
Se poate specifica un singur câmp după care se face ordonarea.
Exemple:
● Sortare crescătoare după id: /api/public/property/?order_by=id
● Sortare descrescătoare după data adăugării: /api/public/property/?order_by=-date_added
Mecanism de reîncercare
În cazul în care un apel către orice feed din acest API întoarce un cod de eroare, trebuie
reîncercat apelul peste 5 minute - de cel puțin 3 ori și de maximum 10 ori.
Atenție! În cazul în care spre exemplu API-ul de proprietăți întoarce o eroare, proprietățile
preluate deja din API nu trebuie șterse. Se va folosi mecanismul de reîncercare, până când
API-ul va răspunde din nou.
Singurul caz în care o proprietate trebuie ștearsă este atunci când apelul API pentru detaliile
proprietății întoarce cod HTTP 404.
În caz că întâmpinați probleme cu accesarea API-ului, vă rugăm să ne scrieți la
suport@crmrebs.com.
Link din CRM către site
Pentru a putea ajunge din CRM la proprietățile importate în site-ul companiei, se va folosi un
endpoint care să redirecționeze spre pagina proprietății din site, în funcție de ID.
De exemplu, pentru proprietatea CP1234 (cu id 1234), se va accesa o adresă de genul
http://siteagentie.ro/id/1234/ care fie va servi direct pagina proprietății, fie va redirecționa către
pagina finală a proprietății. Nu e obligatoriu /id/1234, poate avea orice formă, atât timp cât
cuprinde ID-ul proprietății.
Endpoint-ul va fi folosit pentru:
● a putea ajunge direct din CRM - pe pagina proprietății de pe site-ul companiei
● a redirecționa clientul din email-ul cu proprietăți propuse de către agent, către site-ul
companiei
● activarea canalelor de publicare care au nevoie de un link al proprietății, cum este
PropertyBook.ro
Vă rugăm să ne contactați la suport@crmrebs.com după ce este implementat endpoint-ul pentru
activarea link-urilor din CRM.
Număr vizualizări proprietate de pe
Site-ul companiei
Pentru a putea înregistra numărul de vizualizări pentru fiecare proprietate în site-urile proprii, am
adăugat câmpul tracking_code în API-ul pentru proprietăți. Conținutul câmpului trebuie inclus

Actualizarea în timp real
Actualizarea proprietăților în timp real
Pentru a putea actualiza proprietățile din site în timp real, în momentul în care se face o
schimbare în CRM, punem la dispoziție un webhook care să semnaleze când se modifică o
proprietate.
Webhook-ul va face un apel POST către un URL setat de dvs. în care se va include ID-ul
proprietății din CRM ca parametru POST cu numele property_id.
Exemplu (presupunem că webhook-ul va fi la http://www.exemplu-agentie.ro/hooks/update):
● Se configurează webhook-ul pe site-ul agenției și se trimite URL-ul către
suport@crmrebs.com
● Un agent modifică proprietatea CP1234
● Se face un apel POST către http://www.exemplu-agentie.ro/hooks/update cu POST
property_id=1234
○ curl -X POST -d "property_id=1234" http://www.exemplu-agentie.ro/hooks/update
● În momentul primirii apelului din webhook, site-ul va apela /api/public/property/1234
pentru a extrage informațiile actualizate despre proprietate.
● Dacă API-ul întoarce cod HTTP 404 înseamnă că în urma modificărilor, proprietatea nu
se mai promovează pe site-ul companiei și trebuie ștearsă.
URL-urile imaginilor proprietății sunt unice, ele vor trebui descărcate din nou doar dacă
URL-ul se schimbă. Schimbarea ordinii imaginilor pe o proprietate nu modifică URL-urile
imaginilor.
În cazul în care webhook-ul nu întoarce un răspuns valid (HTTP 200), se va reîncerca apelul de
un maxim de 3 ori la intervale de câte 5 minute.
Chiar și cu folosirea webhook-ului, recomandăm ca periodic (de exemplu o dată pe zi) să se facă
parcurgerea completă a feed-ului de proprietăți din API pentru a evita potențiale inconsistențe
cauzate de erori de comunicare între site și CRM.
Pentru testare, recomandăm folosirea unui tool precum cURL sau http://requestmaker.com/ cu
body-ul property_id=1234.
Actualizarea agenților în timp real
Similar proprietăților, se poate trimite un webhook și la modificarea datelor oricărui agent.
Webhook-ul pentru actualizarea agenților este diferit de cel pentru proprietăți.
Acesta va primi prin POST un parametru cu numele user_id.
Exemplu:
● Se modifică un agent cu ID-ul 100
● Se face un apel POST către http://www.exemplu-agentie.ro/hooks/update_agent cu
POST user_id=100
○ curl -X POST -d "user_id=100"
http://www.exemplu-agentie.ro/hooks/update_agent
Exportarea proprietăților cu altă
valabilitate
În mod implicit, în feed apar numai proprietățile cu valabilitate “Activă” în CRM (cele care au
availability=1).
În cazul în care doriți să apară în API și proprietăți cu altă valabilitate (de exemplu dacă doriți să
afișați în site și proprietăți care au fost deja tranzacționate), va rugăm să luați legătura cu
managerul agenției, pentru a include și alte valabilități din modulul de administrare CRM,
secțiunea Promovare Site Propriu.

● Pentru ansambluri rezidențiale, nu există un singur câmp agent, ci există 2 câmpuri de
tip listă care pot conține mai mulți utilizatori:
○ project_managers - Manageri de proiect pentru ansamblul rezidențial
○ agents - Agenții de vânzare pentru ansamblul rezidențial
Adăugare de cereri
Pentru adăugarea de cereri prin API, se va face un apel HTTP POST către
/api/public/addrequest/
În body-ul request-ului, se vor transmite următoarele câmpuri:
● name - Nume client
● phone - Telefon client
● email - Email
● lead_source - Câmp text pentru sursă lead. Trebuie să existe în CRM o sursă lead cu
nume identic, altfel va fi ignorat
● lead_property - Un ID de proprietate (de exemplu 1234 pentru CP1234), dacă clientul
este interesat de o proprietate anume
○ Se poate folosi și ID-ul intern în loc de ID-ul atribuit de către CRM REBS
● lead_residential_complex - Un ID de ansamblu rezidențial, dacă clientul este interesat
de un ansamblu rezidențial. Acest câmp este opțional
● external_id - Un ID extern care identifică unic cererea. Este folosit pentru a detecta dacă
a fost deja adăugată această cerere, cu scopul prevenirii intrărilor duplicate
● message - Un mesaj introdus de către client. Va apărea pe cerere ca o activitate
finalizată
În caz de succes, se va returna cod HTTP 200 și un JSON de forma:
{
"success": true,
"contact": 123,
"request": 1234
}
În caz de eroare, se va returna cod HTTP 4xx și un JSON de forma:
{
"success": false,
"error": "Un mesaj de eroare aici"
}

Parcurgerea feed-ului
Pentru importul proprietăților din CRM REBS, se va consuma un feed JSON care conține o listă
cu detaliile tuturor proprietăților active.
Recomandăm parcurgerea feed-ului la un interval prestabilit de timp (de exemplu o oră) printr-un
mecanism de gen Cron. Job-ul cron va parcurge toate proprietățile din feed, va salva proprietățile
noi în baza de date proprie, va actualiza proprietățile care au fost modificate, și le va șterge pe
cele care nu mai apar în feed.
Feed-ul este disponibil la /api/public/property/
Există și un feed pentru toti agenții activi, disponibil la /api/public/agent/
Autentificare
Pentru autentificarea la API, se folosește o cheie API care trebuie transmisă la accesarea
oricărei resurse API.
Cheia API poate fi specificată printr-un parametru GET cu numele api_key sau prin header-ul
HTTP Authorization.
De exemplu, dacă cheia API este abcdef, se poate accesa API-ul în următoarele moduri:
● Prin parametru GET: /api/public/property/?api_key=abcdef
● Prin header-ul HTTP Authorization (exemplu folosind curl):
○ curl -H "Authorization: abcdef" http://towerimob.crmrebs.com/api/public/property/
Dacă echipa REBS nu v-a transmis o cheie API, vă rugăm să ne contactați la
suport@crmrebs.com și să includeți în CC și pe managerul companiei pentru care se
implementează API-ul.
Câmpul "meta"
Pentru evitarea timpului de răspuns mare și a unei dimensiuni mari, recomandăm parcurgerea
API-ului folosind paginare. Pentru aceasta, se va folosi câmpul meta din răspuns.
Câmpul meta conține informații utile pentru paginare:
● limit - numărul maxim de proprietăți returnate într-o pagină
● next - URL-ul către pagina următoare, dacă există
● offset - numărul proprietății de la care se returnează proprietăți pentru această pagină
● previous - URL-ul către pagină anterioară, dacă există
● total_count - numărul total de proprietăți (pentru toate paginile)
Pentru o parcurgere cât mai ușoară a API-ului, se poate face un request inițial pentru prima
pagină, iar apoi se parcurge pagină cu pagină folosind câmpul next, până când acesta devine
null.
În mod implicit, o pagină conține 20 de proprietăți. Se pot cere mai multe proprietăți folosind
parametrul limit.
Exemplu:
● Se accesează prima pagină: /api/public/property/
● Se accesează apoi câmpul meta.next din răspuns:
/api/public/property/?offset=20&limit=20
● Și așa mai departe, până când câmpul meta.next devine null, moment în care au fost
parcurse toate proprietățile

Imagini
Imaginile redimensionate la maxim 1920 px x 1080 px sunt returnate în câmpul resized_images,
reprezentat printr-o listă de URL-uri către imagini.
Imaginile neredimensionate sunt returnate în câmpul full_images.
Aceste imagini nu pot fi folosite direct în site. Ele trebuie descărcate, stocate pe serverele
site-ului și servite de acolo către vizitatori.
Pentru a seta un watermark pe toate imaginile, trimite-ne la adresa suport@crmrebs.com o
imagine semitransparentă (PNG).
Ordonare
Ordonare
Proprietățile returnate pot fi ordonate specificând parametrul order_by, ce va avea ca valoare
numele câmpului după care se va face ordonarea. În mod implicit, ordonarea se face crescător.
Pentru ordonare descrescătoare, se va adaugă “-” (caracterul minus) în fața câmpului după care
se face ordonarea.
Se poate specifica un singur câmp după care se face ordonarea.
Exemple:
● Sortare crescătoare după id: /api/public/property/?order_by=id
● Sortare descrescătoare după data adăugării: /api/public/property/?order_by=-date_added
Mecanism de reîncercare
În cazul în care un apel către orice feed din acest API întoarce un cod de eroare, trebuie
reîncercat apelul peste 5 minute - de cel puțin 3 ori și de maximum 10 ori.
Atenție! În cazul în care spre exemplu API-ul de proprietăți întoarce o eroare, proprietățile
preluate deja din API nu trebuie șterse. Se va folosi mecanismul de reîncercare, până când
API-ul va răspunde din nou.
Singurul caz în care o proprietate trebuie ștearsă este atunci când apelul API pentru detaliile
proprietății întoarce cod HTTP 404.
În caz că întâmpinați probleme cu accesarea API-ului, vă rugăm să ne scrieți la
suport@crmrebs.com.
Link din CRM către site
Pentru a putea ajunge din CRM la proprietățile importate în site-ul companiei, se va folosi un
endpoint care să redirecționeze spre pagina proprietății din site, în funcție de ID.
De exemplu, pentru proprietatea CP1234 (cu id 1234), se va accesa o adresă de genul
http://siteagentie.ro/id/1234/ care fie va servi direct pagina proprietății, fie va redirecționa către
pagina finală a proprietății. Nu e obligatoriu /id/1234, poate avea orice formă, atât timp cât
cuprinde ID-ul proprietății.
Endpoint-ul va fi folosit pentru:
● a putea ajunge direct din CRM - pe pagina proprietății de pe site-ul companiei
● a redirecționa clientul din email-ul cu proprietăți propuse de către agent, către site-ul
companiei
● activarea canalelor de publicare care au nevoie de un link al proprietății, cum este
PropertyBook.ro
Vă rugăm să ne contactați la suport@crmrebs.com după ce este implementat endpoint-ul pentru
activarea link-urilor din CRM.
Număr vizualizări proprietate de pe
Site-ul companiei
Pentru a putea înregistra numărul de vizualizări pentru fiecare proprietate în site-urile proprii, am
adăugat câmpul tracking_code în API-ul pentru proprietăți. Conținutul câmpului trebuie inclus
oriunde pe pagina de detalii a proprietății, o singură dată, iar vizitele se vor înregistra automat în
CRM REBS.
Statisticile despre vizualizările proprietăților vor fi disponibile în modulul Rapoarte CRM REBS și
în rapoarte trimise automat din CRM REBS către proprietari.
Actualizarea în timp real
Actualizarea proprietăților în timp real
Pentru a putea actualiza proprietățile din site în timp real, în momentul în care se face o
schimbare în CRM, punem la dispoziție un webhook care să semnaleze când se modifică o
proprietate.
Webhook-ul va face un apel POST către un URL setat de dvs. în care se va include ID-ul
proprietății din CRM ca parametru POST cu numele property_id.
Exemplu (presupunem că webhook-ul va fi la http://www.exemplu-agentie.ro/hooks/update):
● Se configurează webhook-ul pe site-ul agenției și se trimite URL-ul către
suport@crmrebs.com
● Un agent modifică proprietatea CP1234
● Se face un apel POST către http://www.exemplu-agentie.ro/hooks/update cu POST
property_id=1234
○ curl -X POST -d "property_id=1234" http://www.exemplu-agentie.ro/hooks/update
● În momentul primirii apelului din webhook, site-ul va apela /api/public/property/1234
pentru a extrage informațiile actualizate despre proprietate.
● Dacă API-ul întoarce cod HTTP 404 înseamnă că în urma modificărilor, proprietatea nu
se mai promovează pe site-ul companiei și trebuie ștearsă.
URL-urile imaginilor proprietății sunt unice, ele vor trebui descărcate din nou doar dacă
URL-ul se schimbă. Schimbarea ordinii imaginilor pe o proprietate nu modifică URL-urile
imaginilor.
În cazul în care webhook-ul nu întoarce un răspuns valid (HTTP 200), se va reîncerca apelul de
un maxim de 3 ori la intervale de câte 5 minute.
Chiar și cu folosirea webhook-ului, recomandăm ca periodic (de exemplu o dată pe zi) să se facă
parcurgerea completă a feed-ului de proprietăți din API pentru a evita potențiale inconsistențe
cauzate de erori de comunicare între site și CRM.
Pentru testare, recomandăm folosirea unui tool precum cURL sau http://requestmaker.com/ cu
body-ul property_id=1234.
Actualizarea agenților în timp real
Similar proprietăților, se poate trimite un webhook și la modificarea datelor oricărui agent.
Webhook-ul pentru actualizarea agenților este diferit de cel pentru proprietăți.

● Pentru ansambluri rezidențiale, nu există un singur câmp agent, ci există 2 câmpuri de

○ agents - Agenții de vânzare pentru ansamblul rezidențial
Adăugare de cereri
Pentru adăugarea de cereri prin API, se va face un apel HTTP POST către
/api/public/addrequest/
În body-ul request-ului, se vor transmite următoarele câmpuri:
● name - Nume client
● phone - Telefon client
● email - Email
● lead_source - Câmp text pentru sursă lead. Trebuie să existe în CRM o sursă lead cu
nume identic, altfel va fi ignorat
● lead_property - Un ID de proprietate (de exemplu 1234 pentru CP1234), dacă clientul
este interesat de o proprietate anume
○ Se poate folosi și ID-ul intern în loc de ID-ul atribuit de către CRM REBS
● lead_residential_complex - Un ID de ansamblu rezidențial, dacă clientul este interesat
de un ansamblu rezidențial. Acest câmp este opțional
● external_id - Un ID extern care identifică unic cererea. Este folosit pentru a detecta dacă
a fost deja adăugată această cerere, cu scopul prevenirii intrărilor duplicate
● message - Un mesaj introdus de către client. Va apărea pe cerere ca o activitate
finalizată
În caz de succes, se va returna cod HTTP 200 și un JSON de forma:
{
"success": true,
"contact": 123,
"request": 1234
}
În caz de eroare, se va returna cod HTTP 4xx și un JSON de forma:
{
"success": false,
"error": "Un mesaj de eroare aici"
}
